# V28 SQLite 日期持久化硬修复报告

## 修复目标

用户反馈：购买日期在退出重进后仍然会变成当日日期，并且没有开启云端同步。

V28 不再继续把问题归因于云端或 UI，而是直接加固“保存、序列化、SQLite 写入、读取、反序列化、表单保存”整条链路。

## 关键修复

1. 资产购买日期不再只保存 ISO 字符串，同时保存三份冗余字段：
   - `purchaseDate`: `yyyy-MM-dd`
   - `purchaseDateYmd`: `yyyy-MM-dd`
   - `purchaseDateEpochDay`: 从 UTC 日期计算出的 epoch day

2. 读取资产时优先读取：
   - `purchaseDateYmd`
   - `purchaseDate`
   - `purchaseDateEpochDay`
   - `createdAt / updatedAt` 作为最后兼容兜底

3. 保存资产时，购买日期必须严格解析成功，失败直接提示，不再静默回退到今天。

4. 新建资产页和编辑资产页均改用严格日期解析：
   - `parseUserDateOrNull`
   - `parseOptionalUserDate`

5. `AppStore.save()` 写入 SQLite 后会立即读回并比较完整 JSON。如果写入后读回内容不一致，会直接抛出错误，避免“页面显示保存了，其实本地没落盘”的假象。

6. `Asset.toMap()` 中日期字段改为日期型字符串，不再把购买日期保存为带时区/时间的 ISO 字符串，避免时区和解析差异。

## 重要说明

如果旧版本已经把某条资产的购买日期覆盖成今天，App 无法自动知道它原本应该是哪一天。V28 能保证的是：重新编辑并保存后的日期不再被静默改回今天。

## 测试建议

1. 安装 V28。
2. 新建资产，购买日期设置为 `2024-01-03`。
3. 保存，杀掉 App 进程。
4. 重新打开，检查购买日期是否仍为 `2024-01-03`。
5. 编辑该资产，改为 `2023-12-20`。
6. 保存，杀掉 App 进程，再打开。
7. 检查是否仍为 `2023-12-20`。
